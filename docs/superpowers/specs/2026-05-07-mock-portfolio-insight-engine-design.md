# Mock Portfolio Insight Engine Design

Date: 2026-05-07

## Goal

Build the first real internal flow for the portfolio insight backend without external market APIs.

The service should not behave like a generic AI stock explainer. It should diagnose what the user's selected assets become as a portfolio: overlapping bets, false diversification, concentration, missing roles, and conditions that should change the decision.

This phase uses deterministic mock data so the full API flow can be tested in Postman before Twelve Data, OpenDART, Upbit, or OpenAI are connected.

## Product Position

The product is a data-driven portfolio diagnosis workflow.

The user selects assets and enters investment constraints. The backend calculates portfolio structure, detects signals, produces concrete actions, and then renders those findings in user-friendly language.

The system must avoid generic statements such as:

- "This asset is volatile."
- "This has long-term growth potential."
- "Diversification is important."
- "This can increase expected return."
- "Monitor market conditions."

Every user-facing insight must explain:

- What relationship between the selected assets was detected.
- Which data or mock metric supports the detection.
- Why the suggested action follows from that signal.
- What condition would make the suggestion worth revisiting.

## Core Principle

Computation, judgment, and expression are separate.

- Code calculates features and portfolio exposures.
- Rule services detect structured signals and actions.
- AI, when enabled later, rewrites structured findings into natural user language.
- Evidence records keep the basis, limitation, and review trigger.

In this mock phase, user-facing explanation is generated by deterministic templates rather than OpenAI.

## API Flow

The first usable flow is:

```http
GET  /api/assets/search?query={query}
POST /api/portfolio-intents
GET  /api/portfolio-intents/{intentId}
POST /api/portfolio-proposals
GET  /api/portfolio-proposals/{proposalId}
GET  /api/evidence/{evidenceId}
```

Proposal generation is synchronous in this phase. `POST /api/portfolio-proposals` creates the proposal result immediately and returns `COMPLETED`.

## Portfolio Exposure Analysis

Portfolio diagnosis must reason about economic exposure, not only asset class labels.

Examples:

- Samsung and SOXL are not simply Korea stock plus US ETF. They may be overlapping semiconductor-cycle exposure.
- TIGER US S&P500 ETF and Bitcoin may both benefit when risk appetite rises, even though one is an equity ETF and the other is crypto.
- Hyundai Motor and a US equity ETF can both be affected by global growth, but Hyundai also has auto-cycle and FX sensitivity.

The analyzer produces:

- tag-level exposure totals.
- leverage-adjusted exposure totals.
- currency exposure totals.
- high-volatility exposure totals.
- concentration by thesis driver.
- pairwise relationship hints from mock correlation profiles.

## Signal Detection

The first signal types are:

### Overlapping Exposure

Detects when multiple assets share the same economic driver.

Example:

Samsung plus SOXL means the portfolio is strongly tied to semiconductor-cycle recovery. If SOXL is large, it can dominate the result because of leverage.

### False Diversification

Detects when assets look diversified by label but behave like the same broad bet.

Example:

TIGER US S&P500 ETF plus Bitcoin can become a risk-appetite bet if recent correlation is high.

### Tactical Product Misuse

Detects leveraged or high-decay products being treated like core holdings.

Example:

SOXL should usually be classified as tactical exposure, not the main long-term holding.

### Missing Stabilizer

Detects when the selected assets are all tied to growth, cycle, liquidity, or high-volatility drivers.

The suggestion should not blindly say "add bonds." It should explain what role is missing and offer candidate role categories.

### Allocation-Conviction Mismatch

Detects when a high-risk or low-confidence asset receives a larger weight than the thesis supports.

## Action Generation

Actions are not generic recommendations. They are portfolio-structure changes.

Action types:

- reduce one of the overlapping assets.
- classify an asset as tactical instead of core.
- cap a high-volatility asset.
- shift new monthly contribution toward a broader or less overlapping asset.
- add a missing role category.
- schedule a review condition.

Actions include:

- affected assets.
- user-facing reason.
- internal basis.
- evidence ids.
- review trigger.

## Recommended Horizon

Risk profile does not determine the recommended horizon.

The horizon is derived from:

- selected assets' momentum windows.
- weighted influence of the highest-conviction drivers.
- earliest review point among high-risk or low-confidence assets.
- catalyst timing.

Risk profile controls:

- max weight for high-volatility assets.
- concentration tolerance.
- leveraged product tolerance.
- monthly contribution aggressiveness.
- acceptable downside in simulation.

## User-Facing Language

User-facing text should explain portfolio relationships in simple language.

Good example:

"This portfolio is not just a mix of Korea, US, and crypto. The S&P500 ETF and Bitcoin can both benefit when investors are willing to take more risk. If recent data shows they are moving together, Bitcoin is not acting as a diversifier here; it is increasing the same upside/downside bet."

Bad example:

"Bitcoin has high volatility and can increase expected return."

The API should return both:

- structured signals for UI rendering.
- user explanation for immediate reading.

## Evidence

Evidence in this phase is deterministic but must keep the future external-data shape.

Each evidence item includes:

- `claim`
- `basis`
- `sourceSnapshots`
- `limitation`
- `reviewTrigger`
- `affectedAssets`

Mock source examples:

- `MOCK_PRICE_RETURN_90D`
- `MOCK_VOLATILITY_30D`
- `MOCK_EXPOSURE_TAGS`
- `MOCK_CORRELATION_PROFILE`
- `MOCK_ETF_PROFILE`
- `MOCK_LEVERAGE_PROFILE`

## Example Diagnosis

For Hyundai Motor, TIGER US S&P500 ETF, and Bitcoin:

The system should examine:

- whether the S&P500 ETF and Bitcoin recently move together as risk assets.
- whether Hyundai adds a distinct auto-cycle and FX-sensitive thesis.
- whether the portfolio is overexposed to global growth and risk appetite.
- whether new monthly money should go to Bitcoin, broad equity, or a stabilizing role.

Possible signal:

"The portfolio looks diversified by asset label, but two selected assets may depend on the same risk-appetite environment. If Bitcoin's recent relationship with US equities is high, it is not mainly diversifying the S&P500 ETF; it is amplifying the same market mood."

Possible action:

"Keep Hyundai as the separate auto-cycle view, keep the S&P500 ETF as the broad core, and cap Bitcoin unless the user explicitly wants a stronger risk-appetite bet. If the user adds monthly contributions, route more of the new money to the broad ETF than to Bitcoin until the correlation signal weakens."

## Testing Expectations

Tests should cover:

- asset search returns seed assets.
- intent creation stores selected asset snapshots.
- proposal creation persists a completed proposal.
- proposal detail includes allocations, horizon, signals, actions, simulation, and evidence ids.
- evidence detail returns claim, basis, limitation, and review trigger.
- overlapping semiconductor exposure is detected for Samsung plus SOXL.
- false diversification is detected for S&P500 ETF plus Bitcoin when mock correlation is high.
- leveraged product misuse is detected when SOXL receives core-like weight.
- risk profile changes caps, not horizon.

## Non-Goals

This phase does not include:

- real market data APIs.
- OpenAI API calls.
- PostgreSQL persistence.
- async job queue.
- brokerage integration.
- authentication.
- investment advice compliance language beyond basic disclaimers.

## Acceptance Criteria

Postman can exercise the full flow from asset search to proposal detail and evidence detail.

The proposal response must contain at least one non-generic insight derived from relationships among the selected assets.

The same input should always produce the same output in mock mode.

The implementation should preserve ports/interfaces so external providers can replace mock data later.
